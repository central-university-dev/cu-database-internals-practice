# Лекция 3. Практические задания

## Практическое задание 1. Простой каталог

### Цель

Познакомиться с устройством системных каталогов баз данных и реализовать их минимальную модель.  
В рамках задания вы разработаете набор классов для описания типов, колонок, таблиц, а также сам каталог и фасад для
работы с ним.

---

### Требования к моделям

#### 1. Класс `Type`

**Назначение:** описывает тип данных колонки.  
**Свойства:**

- `name: String` — имя типа (например, `"INT"`, `"VARCHAR"`).
- `byteLength: int` — длина в байтах (положительное число или -1).

**Ограничения:**

- Имя не пустое.
- `byteLength > 0 || byteLength == -1`.

---

#### 2. Класс `Column`

**Назначение:** описывает колонку таблицы.  
**Свойства:**

- `name: String` — имя колонки.
- `type: Type` — тип данных колонки.

**Ограничения:**

- Имя не пустое.
- Тип не может быть `null`.

---

#### 3. Класс `Table`

**Назначение:** описывает таблицу.  
**Свойства:**

- `name: String` — имя таблицы.
- `columns: List<Column>` — список колонок.

**Ограничения:**

- Имя не пустое.
- Список колонок не пуст.
- Имена колонок уникальны внутри таблицы (без учёта регистра).

---

#### 4. Класс `CatalogManager`

**Назначение:** in-memory хранилище схем таблиц.  
**Свойства:**

- Коллекция таблиц с уникальными именами (регистронезависимыми).

**Методы:**

- `createTable(Table table)` — добавить таблицу.
- `dropTable(String name)` — удалить таблицу.
- `getTable(String name): Table` — получить таблицу по имени.
- `listTables(): Set<String>` — перечислить имена таблиц.

---

## Практическое задание 2. Сложный каталог

### Цель

Усложнить дизайн каталога СУБД: метаданные таблиц и колонок больше **не хранятся вложенными объектами**.  
Вместо этого все сущности записываются в отдельные реестры (списки/таблицы) и **собираются в привычную иерархию по
требованию** по связям через `oid`.

---

### Концепция и требования

#### 1. Разделённое хранение

Вместо `Catalog{ tables: List<Table{ columns: [...] }] }` реализовать **плоские каталоги**:

- `TableDefinition` — описания таблиц (каталог таблиц)
- `ColumnDefinition` — описания колонок (каталог колонок)
- `TypeDefinition` — описания типов (каталог типов)

> Собранные представления (`Table`, `Column`) должны конструироваться из реестров при обращении, используя связи `oid`.

#### 2. Связи через OID

Каждая сущность имеет уникальный `oid: long` (или `UUID` — на ваше усмотрение, но единообразно во всём проекте).

- `TableDefinition.oid` — первичный идентификатор таблицы.
- `ColumnDefinition.tableOid` — внешний ключ на `TableDefinition.oid`.
- `ColumnDefinition.typeOid` — внешний ключ на `TypeDefinition.oid`.

#### 3. Дополнительные поля

##### `TableDefinition`

- `oid: Int`
- `name: String`
- `type: String = "table"` (фиксированное значение)
- `fileNode: String = "<oid>.dat"` — имя узла хранения данных таблицы
- `pages: int = 0` — количество страниц данных таблицы (начально 0)

##### `ColumnDefinition`

- `typeOid: Int`
- `tableOid: Int` — связь с таблицей
- `name: String`
- `type: Definition`
- `position: int` — **номер поля в таблице** (начиная с 0, без пропусков для каждой таблицы)

---

## Собранные представления (in-memory views)

Для совместимости с API из Практики 1 требуется уметь собирать:

- `Table { name, columns: List<Column> }`
- `Column { name, type }`

Сборка выполняется CatalogManager, который:

1. Находит `TableDefinition` по имени или `oid`.
2. Загружает все `ColumnDefinition` с `tableOid = TableDefinition.oid`, сортирует по `position`.
3. Возвращает собранный `Table`.
4. В каждом объекте прошлой практики необходимо хранить ссылку на соответствующий новый класс, представляющий каталог.

---

## Практическое задание 3: Каталог и файловая система

### Цель

Научиться работать с каталогом БД не напрямую в оперативной памяти, а **через слой страниц и буферный менеджер**.  
Теперь метаданные каталога должны храниться на диске в формате страниц и загружаться в память только через
предоставленный интерфейс `BufferManager`.

---

### Исходные условия

У вас уже есть:

- реализация **буферного менеджера** (`BufferManager`) с методами для получения, записи, закрепления и отпускания
  страниц.
- класс `Page` и его конкретизация `HeapPage`.
- результат практической работы 2: разделённые `TableDefinition` и `ColumnDefinition`, сборка представлений `Table`/
  `Column`, работа через `CatalogManager`.

---

### Новые требования

#### 1. Хранение в страницах

- Каталог в наборе страниц.
- Каждая страница содержит записи одного типа:
    - страницы с `TableDefinition`,
    - страницы с `ColumnDefinition`,
    - страницы с `TypeDefinition`.
- Страницы разных типов хранятся в разных файлах:
    - `table_definitions.dat` — страницы с `TableDefinition`.
    - `column_definitions.dat` — страницы с `ColumnDefinition`.
    - `types_definitions.dat` — страницы с `TypeDefinition`.
- Страница может хранить несколько записей подряд, пока хватает места.

#### 2. Формат записи

- `TableDefinition` и `ColumnDefinition` и `TypeDefinition` должны уметь:
    - сериализоваться в массив байт (метод `toBytes()`),
    - восстанавливаться из массива байт (метод `fromBytes(byte[])`).
- Размер записи ограничен размером страницы.

#### 4. CatalogManager

Необходимо модифицировать `CatalogManager`, чтобы все операции (на текущий момент - создание таблицы) работали через слой страниц и буферный менеджер.  

Алгоритм:

1. Считать нужную страницу через `BufferManager.get()`.
2. Найти или вставить запись `TableDefinition`/`ColumnDefinition` / `TypeDefinition`.
3. При изменении записать страницу обратно через `BufferManager.write()`.
4. Создать файл для хранения данных таблицы, если он ещё не существует по fileNode.

При старте работы системы менеджер каталога должен прочитать все страницы каталога и положить во внутреннюю структуру.

## Практическое задание 4: Работа с данными через каталог

### Цель
Расширить функциональность СУБД: добавить слой **операций с данными**, который работает через каталог БД и буферный менеджер.  
Теперь помимо хранения схемы (таблиц, колонок, типов) необходимо уметь **вставлять строки в таблицу** и **извлекать их обратно**, пользуясь метаданными из каталога.

---

### Новые сущности

#### OperationManager
Фасад для выполнения операций с данными.

**Методы:**
- `insert(String table, Object... params)`
  - Находит таблицу по имени через `CatalogManager`.
  - Проверяет, что количество параметров соответствует колонкам.
  - Сериализует кортеж в байтовое представление (согласно типам колонок).
  - Записывает запись в первую подходящую страницу таблицы через `BufferManager` (или создаёт новую страницу при нехватке места).
  - Обновляет счётчик `pages` в `TableDefinition`.

- `List<List<Object>> get(String table)`
  - Находит таблицу по имени.
  - Сканирует все её страницы.
  - Читает кортежи, десериализует значения в соответствии с типами колонок.
  - Возвращает список строк, каждая строка — список объектов (`List<Object>`).

---

### Требования к реализации

#### 1. Использование каталога
- Описание таблицы (`TableDefinition`) и колонок (`ColumnDefinition`) берётся из каталога.
- Типы колонок (`Type`) определяют способ сериализации и десериализации значений:
  - `INT` → 4 байта,
  - `VARCHAR_256` → длина + содержимое (ограничение `256` байтов),

#### 2. Формат хранения строки
- Строка = последовательность полей, сериализованных подряд в байтовый массив.
- Для переменных типов (например, `VARCHAR`) хранится длина + байты значения.
- Строки размещаются в `HeapPage`.
